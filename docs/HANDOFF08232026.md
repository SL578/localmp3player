## What this is

A native iOS music player for mp3 files the user imports themselves. Fully
offline: no backend, no accounts, no network calls of any kind, free, no IAP.

Differentiators vs. existing local players (e.g. Doppler): messy-filename →
metadata cleanup, rules-based smart playlists, smarter duplicate handling, and
CarPlay treated as a first-class surface rather than bolted on.

**Stack:** Swift + SwiftUI, Core Data, AVFoundation, CarPlay framework.
**Deployment target:** iOS 17.0. **Swift:** 5.0. **Bundle ID:** `lin.localmp3player`.

## Build and run

`xcode-select` points at CommandLineTools, so command-line builds **must** set
`DEVELOPER_DIR`:

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project localmp3player.xcodeproj -scheme localmp3player -destination 'platform=iOS Simulator,name=iPhone 17' build
```

Install and launch on the booted simulator:

```bash
xcrun simctl install booted <path-to>/localmp3player.app && xcrun simctl launch booted lin.localmp3player
```

Builds clean with zero warnings. Opening in Xcode works normally.

## Architecture

```
Model/      Core Data entities + hand-written NSManagedObject subclasses (codegen off)
Library/    LibraryQuery, SmartPlaylistEngine  ← the shared query layer
Import/     document picker, filename parser, ID3 reader, import/duplicate coordinator
Playback/   PlaybackController — AVAudioPlayer, queue, now-playing, remote commands
CarPlay/    scene delegate + browse-template builder
UI/         SwiftUI screens
Style/      UIMode (Standard/Performance seam), Theme (appearance + user colors)
```

**The one rule that matters:** `LibraryQuery` and `SmartPlaylistEngine` are the
only places that decide which songs belong to a playlist, tag, or rule. Both the
phone screens and the CarPlay templates read from them, so a change lands on both
surfaces at once. Don't fork this logic.

## What's built and verified working

All verified live in the iOS Simulator, not just compiled.

- **Import** — document picker copies into app storage, batch supported. ID3
  wins; `FilenameParser` is the fallback (strips bracketed noise, splits
  `Artist - Title`). Editable review sheet before save, with a one-tap
  title/artist swap. Parser checked against 19 real-world messy filenames.
- **Duplicates** — `normalizedKey` lookup with Replace / Keep Both / Replace All.
- **Tagging** — per-song and multi-select batch tagging (tri-state for partial
  selections), color-coded chips.
- **Playlists** — manual (create, add via multi-select, drag-reorder, order
  persisted in `PlaylistEntry.position`) and smart (all 6 rule types, live
  `NSFetchRequest` evaluation, live match-count preview in the editor).
- **Playback** — queue, background audio, lock-screen remote commands, play
  count / last-played tracking.
- **Shuffle & repeat** — queue kept twice (`orderedQueue` browse order + `queue`
  play order) so toggling shuffle off restores the original order without
  reloading the track. Repeat cycles off → all → one; **repeat-one applies only
  on natural track end** — pressing next always advances, per platform
  convention. `shufflePlay` ("play something random") is on the toolbar of the
  Library, every playlist, smart playlist, and tag. Both wired to system remote
  commands so lock screen and CarPlay can drive them.
- **Appearance** — System / Light / Dark / Dynamic. Every color is a
  `ThemeColorToken` case with a picker in Settings; light and dark store
  overrides separately, each resettable. Persists across relaunch.
- **Display Mode** — Standard vs Performance, one styling seam.
- **CarPlay** — browse hierarchy built and linked into the binary and scene
  manifest. **Not visually verifiable** without a real head unit.

## Decisions worth not re-litigating

**CarPlay uses the modern template API, not `MPPlayableContentDataSource`.**
The original spec named that API; it has been deprecated since iOS 14 and
CarPlay no longer calls it. Uses `CPTemplateApplicationSceneDelegate`,
`CPTabBarTemplate`, `CPListTemplate`, `CPNowPlayingTemplate` instead. The
structure the spec asked for is unchanged: playlists (smart first) → tags →
songs, playback one tap from any list.

**The bottom bar is hand-rolled, not a `TabView`.** Two reasons, both learned
the hard way: the iOS 26 system tab bar always draws a glass material, which
Performance mode must be able to turn off; and attaching the mini player as a
`tabViewBottomAccessory` when playback started restructured the view tree, which
reset the selected tab back to Library mid-navigation. That was the user's
original bug report. Don't reintroduce a `TabView` here.

**`modeNavigationChrome` is only safe on inline titles.** A visible
`toolbarBackground` hides a *large* navigation title on iOS 26 — it silently
swallowed the "Settings" heading before this was scoped down.

**Dynamic appearance uses fixed hours, not real sunset.** `DaylightWindow`:
dark 19:00–07:00. Real sunset times would need location access or a network
call, and the app is strictly offline. Deliberate.

**Tapping a song pushes the player for that list**, so the visible queue is
exactly what was played from and nothing else. Also a direct user request.

## Known issues / open items

- **CarPlay entitlement not yet requested.** Manual approval from Apple
  (https://developer.apple.com/contact/carplay/), done once the app is otherwise
  complete. `localmp3player.entitlements` is intentionally empty — adding the key
  without a matching provisioning profile breaks device signing. Tracked in the
  repo README.
- **`ArtworkCache` decodes synchronously on the main thread** on first hit
  (`UI/LibraryView.swift`). Invisible with a handful of songs; a large library
  could hitch on first scroll through fresh artwork. Move to a background decode
  if it shows up. Left synchronous deliberately to avoid async complexity that
  may not be needed.
- **Drag-to-reorder was never confirmed via simulator automation.** The UI is
  wired correctly (`onMove` → `reorder(to:)`, `EditButton`, drag handles and
  delete controls all render); synthetic touch paths just couldn't reliably
  drive the gesture. Worth a manual check.
- No unit test target exists. Parser correctness was checked by inspection
  against sample filenames, not by automated tests.

## Working notes for the simulator

- Point coordinate space is **402 × 874** on iPhone 17; screenshots come back at
  919 × 1961. Scale taps by ~0.437 (x) / ~0.446 (y) or taps land in the wrong place.
  This wasted a lot of time early on.
- `control` action `attach` reports the correct point dimensions — call it first.

## Out of scope by design

Android / Android Auto (no cross-platform abstraction — explicitly not wanted
now), any in-app song acquisition or YouTube functionality (must stay out for
App Store compliance), monetization of any kind, cloud sync, accounts, social.

## User preferences observed

- Wants Performance Mode described as a general efficiency mode, **not** framed
  around driving. It's an mp3 player that happens to support CarPlay well, not a
  product marketed at driving enthusiasts. Keep marketing/UI copy neutral.
- Reports bugs by observed symptom and expects the underlying cause found, not
  the symptom patched.
- Prefers being told when something was deliberately left out and why.
