### The stale-bundle trap, still true

`xcrun simctl install` exits 0 and creates a new bundle directory, but
`xcrun simctl launch <old-identifier>` starts whatever was installed under the
*old* identifier. **"BUILD SUCCEEDED" plus a successful install is not evidence
that the app on screen is your build.**

**Grepping the debug dylib for a new string only works if the change added one.**
What works for any change is comparing the installed dylib against the build
product. This one-liner is what was used all session — it prints `1` when the
running bundle is your build and `2` when it is not:

```bash
RB=$(ps -Ao comm | grep localmp3player.app/localmp3player | head -1)
shasum "$(dirname "$RB")/localmp3player.debug.dylib" "$BP/localmp3player.debug.dylib" | awk '{print $1}' | sort -u | wc -l
```

### `simctl uninstall` is never the answer

It **deletes the app's data container** — library, tags, playlists, palette,
interface mode, everything. `xcrun simctl install` over the existing install
registers new PlugIns fine.

If an uninstall is genuinely unavoidable, back the data container up *and verify
the copy* first:

```bash
cp -R "$(xcrun simctl get_app_container <UDID> com.lin.localmp3player data)/" backup/
```

### The scheme trap, if another target is ever hand-added

The project had **no `.xcscheme` files at all** — Xcode autocreated one per
target. Adding `ShareExtension` added a scheme, and with equal order hints Xcode
picks the alphabetically first: capital `S` sorts before lowercase `l`, so the
picker silently switched and ⌘R started asking "choose an app to run".

Fixed by committing a real shared scheme at
`localmp3player.xcodeproj/xcshareddata/xcschemes/localmp3player.xcscheme`, and
hiding the ShareExtension scheme in the user's `xcschememanagement.plist`
(`xcuserdata/` is gitignored, so that half is local only).

**Editing scheme files while Xcode is running does nothing.** The active scheme
lives in Xcode's in-memory UI state. Restarting Xcode is what applied it.

### Logging from the simulator

`NSLog` and `print` do **not** reach `xcrun simctl spawn <UDID> log show`, and
`--console-pty` redirected to a file captures nothing. What works is writing to a
file in the app's own Documents directory and reading it from the host.

## What changed this session

One commit, `cc0e29e`.

### The toolbar's glass no longer samples content in Performance mode (`cc0e29e`)

**Symptom as reported:** *"the performance mode player return chevron changing
colours when you scroll to different parts of the screen."* With two screenshots
attached: lighter when the chevron is near the artwork, back to normal when you
drag further.

**Cause, measured rather than guessed.** The chevron glyph never moved — it is
`theme.accent` and stayed `#0a84ff` at every scroll position. What changed is the
**Liquid Glass capsule iOS 26 draws behind a navigation-bar button**, and the
load-bearing fact is:

> **That capsule samples the scroll content behind the bar, not the bar's own
> fill.**

Which is why `modeNavigationChrome`'s pinned opaque background never had a chance
of stopping it. The bar itself measured pure black at every position tested.
Sampled on the capsule's fill either side of the glyph:

| scroll position | capsule fill |
| --- | --- |
| at top, artwork well below the bar | rgb(25,25,25) |
| artwork passing behind the bar | rgb(46,46,46) |
| artwork scrolled past | rgb(25,25,25) |

Non-monotonic, which is what makes it the user's description exactly and what
rules out a scroll-edge state change.

In Standard mode that is a cross-fade and reads as the glass doing its job. In
Performance mode `UIView.setAnimationsEnabled(false)` turns it into a hard step —
the same shape as every other interactive transition this mode breaks.

**The fix.** A capsule is a material, and Performance mode already refuses
materials everywhere else; this one was only missed because the *system* draws it
rather than the app asking for it. `modeToolbar(_:content:)` in
`ModeStyling.swift` wraps `.toolbar` and hands iOS 26's
`sharedBackgroundVisibility` the mode's answer — `.automatic` in Standard,
`.hidden` in Performance.

Three details are load-bearing:

- **It is a wrapper, not a modifier applied afterwards, and
  `modeToolbarBackground` is `fileprivate`.** A `.toolbar` written the plain way
  silently opts back into the sampling glass, with nothing to notice at the call
  site. Going through `modeToolbar` is the only way to declare a toolbar now, so
  a new screen cannot forget. **There is deliberately no way to call the
  underlying modifier directly.**
- **The mode is passed as a value, not branched on.** `sharedBackgroundVisibility(
  mode.usesMaterials ? .automatic : .hidden)` rather than an `if` — same reason as
  `modeTransactions`: a branch in a `@ToolbarContentBuilder` is a change of
  structural identity. Only the `#available(iOS 26.0, *)` check is a branch, and
  that is fixed for the life of the process.
- **All 19 toolbars, not just Now Playing.** Fixing one screen would leave bare
  glyphs on some bars and glass capsules on others *in the same mode*, which is
  worse than either. Ten structs gained `@Environment(\.uiMode)` to reach it:
  `PlaylistPickerView`, `SongEditor`, `ImportDraftEditor`, `SmartPlaylistEditor`,
  `CriteriaPicker`, `PlaylistEditor`, `SongPickerView`, `TagEditor`,
  `EntityColorPicker`, `BatchTagEditor`.

**What was tried and does not work:** `.buttonStyle(.plain)` on the button. It
was the obvious first guess and it changes nothing — the capsule belongs to the
`ToolbarItem`, not to the `Button`. Verified on a real build, not reasoned about.
There is also **no View-level API for this**; the SDK's only lever is on
`ToolbarContent`, which is why the helper is shaped the way it is.

**Verified:** Performance mode player at the top of the scroll, mid-artwork and
past it — rgb(0,0,0) throughout — and the chevron still dismisses the player.
Library, Playlists, Tags roots and the tag detail all consistent. Standard mode
unregressed: capsules present, sheet card and inset unchanged.

**Visible side effect, stated plainly:** in Performance mode every toolbar button
in the app is now a bare glyph on the opaque themed bar, with no capsule behind
it. That is the pre-iOS-26 look. It was not vetoed because it was not offered
separately — it *is* the fix.

## Decisions worth not re-litigating

**iOS 26's toolbar-button glass samples the content behind the bar, not the
bar.** New this session. A pinned opaque `toolbarBackground` does not stop it.
If any bar control's appearance shifts with scroll position, this is why — start
by measuring pixels, not by reading the toolbar-background code.

**Measure the pixels.** New this session, and it is the reason this bug closed in
one session after failing in the last. Screenshots looked at by eye did not
settle it; sampling the capsule's fill at three scroll positions settled it in
four calls and produced the non-monotonic reading that identified the mechanism.
A tiny `NSBitmapImageRep` sampler over `xcrun simctl io ... screenshot` is enough.

**Every toolbar goes through `modeToolbar`.** New this session. Not a style
preference — the thing it turns off is drawn whether or not the app asks for it,
so a plain `.toolbar` is an invisible regression.

Carried over and still true:

**Performance mode's `UIView.setAnimationsEnabled(false)` makes interactive
transitions look broken.** Anything gesture-driven that ends in a UIKit
completion animation will snap instead. The ruling was to remove the gesture
rather than to carve an exception into the mode — *"that's the only thing that
impacts user experience."* This session added a second shape of the same problem:
a system-driven *cross-fade* becomes a hard step. The answer there was to remove
the thing being faded, not to re-enable the fade.

**A pinned toolbar background and a large title are mutually exclusive on iOS
26.** `modeNavigationChrome` takes a `ModeTitleStyle` that must match the
screen's real `navigationBarTitleDisplayMode`. Getting it wrong either hides the
title or lets content show through the bar. **When a helper's doc comment already
states a constraint, honour it per call site rather than changing the helper for
everyone.**

**A swipe action that only raises a confirmation must not carry
`role: .destructive`.** The role makes UIKit animate the row away before the
prompt appears. State `.tint(.red)` instead. Actions that really do remove their
row keep the role.

**`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` is set on this project.** Anything
that needs to be off the main thread must say so explicitly — `nonisolated` plus
`Task.detached`. A bare `async` function is not enough here.

**`PlaybackClock` is held as a plain `let`.** Making it `@Published`, or adding a
`currentTime` passthrough on the controller, puts the 1 Hz rebuild straight back.

**The player is a `fullScreenCover` in Performance and a `sheet` in Standard.**
Both modifiers are always applied, gated on mode-aware bindings so exactly one is
live; an `if` between them would restructure the view tree on a mode change.
`.interactiveDismissDisabled` was tried and is not enough — it blocks the
dismissal, not the drag.

**Don't hand-roll a gesture that competes with `List`'s own recognizers.** Adding
a fourth recognizer to shorten a swipe produced three defects and no benefit the
user valued.

**Never measure a List row with a `GeometryReader` that writes `@State`.** The
write lands during cell configuration and can leave `swipeActions` unbuilt.

**Never put a custom `ButtonStyle` in a List's environment.** `swipeActions`
builds its actions from the `Button`s you declare, and with a custom style in
scope it produces *none*. Buttons inside lists use `accentAction(theme)`.
(`.buttonStyle(.plain)` on a *toolbar* button is not this — it is harmless, and
also useless; see above.)

**An explicit `foregroundStyle` outranks `.tint`.**

**An SF Symbol does not inherit a foreground style set on its enclosing
`Button`; a `Text` does.** Colour toolbar glyphs on the `Image`, via
`ToolbarGlyph`; text buttons use `.toolbarTint()`.

**Test presentation dimming in Standard mode.** Performance mode has no
presentation animation to see it in.

**The mini bar is the only way into the full player.** Tapping a song plays it
and stays put. One player screen, one design, dismissed by a leading chevron.

**Multi-file sharing needs a share extension. Full stop.** And **iOS will not let
a share extension launch its host app.**

**Ordering matters in the extension.** Calling `completeRequest` before the
asynchronous `open` tears the extension down and the open never lands.

**One `PBXFileSystemSynchronizedRootGroup` can be listed in two targets'
`fileSystemSynchronizedGroups`**, which is how `Shared/` reaches both.

**Tag exclusions use `SUBQUERY(...).@count == 0`,** not `NOT (ANY tags.id == x)`.

**`SmartPlaylistDetailView` renders an array, not a `@FetchRequest`.**

**Settings pushes by value.** **`EditButton` is not used anywhere.** **Delete
confirmations show only a Delete button.** **Sliders mean edit, a pencil means
rename.** **Core Data gets a new model version rather than an edit in place.**
**Playlist selection is keyed by `PlaylistEntry.id`.** **Toolbar item budget on a
pushed screen is four compact trailing icons with a short title.** **Tab panes
are kept alive behind an opacity change,** so `popSignal` exists.

**Don't trust `Slider.onEditingChanged` for "the drag ended" on iOS 26.**

**`ScrubBar` uses `highPriorityGesture`, not `gesture`.**

**A `play()` re-issue after setting `AVAudioPlayer.currentTime` is not needed.**

**`AudioFileStore.stageFile` must not delete its source unconditionally.**

**An incoming share must not enter the scanning phase while the review sheet is
open.**

**Incoming URLs are buffered for 400ms before staging.**

**Parser rules are deliberately narrow, each guarded by the case that would
break it.** `AC/DC`, `20 ft Under`, `Level 42`, `Sum 41` all survive.

## Working notes for the simulator

- **The project uses Xcode 16 file-system-synchronized groups.** New and deleted
  files on disk are picked up with no `project.pbxproj` edit. New *targets* still
  need one.
- Simulator: **iPhone 17, `D4DACBFD-572D-42AB-96AF-6FD72E2A3562`**.
  Device: **iPhone 16, `EFEEEBD5-61F7-5EEF-AEAD-A1F827571239`**.
- **Native screenshots are 1206 × 2622; point space is 402 × 874.** That is a
  clean **×3**. Note this is *not* the ~2.29 the previous handoff quoted — that
  figure was for the resized image the simulator tool returns, not for
  `xcrun simctl io ... screenshot`. **Use `simctl io` and divide by 3** when you
  need pixel-accurate coordinates.
- **Sampling pixels is the way to settle a colour question.** `sips -Z 500` to
  look at a screenshot, and a small Swift `NSBitmapImageRep` tool to read exact
  values. Both were built in the scratchpad this session; neither is in the repo.
- **`touch_path` beats `swipe` for controlled scrolling.** A `swipe` flings and
  overshoots by hundreds of points. A five-point `touch_path` with `dt_ms` of
  150–400 and a repeated final point lands roughly where aimed and settles before
  the screenshot.
- **Horizontal swipes need a duration.** `swipe` with `duration: 0.8` works. A
  swipe or drag starting within 4pt of a screen edge performs the OS edge gesture
  instead — start further in.
- **A tab remembers where you left it**, so tapping a tab may land on a pushed
  detail screen. Screenshot before tapping by coordinate.
- **The mini bar shifts every row below it**, and it sits *above* the tab bar —
  aim for its vertical middle (~757pt in Performance), not its top edge, or the
  tap goes to the list row behind it.
- **Performance mode changes the bottom bar's layout** — captioned icons at
  y≈819 rather than the Standard pill row at y≈808. Screenshot after switching.
- **Tapping the Library search field opens the keyboard and a paste menu.** Two
  taps to get back out. Aim at song rows, not the top of the list.
- **The user tests alongside you in the same simulator.** Don't assume the app
  state is yours.

stale-bundle trap mean "BUILD SUCCEEDED" proves nothing.

**They diagnose their own bugs, and the diagnosis is usually right.** Confirmed
again this session, emphatically: they supplied two screenshots and the sentence
*"the colour changes when the chevron gets close to the music thumbnail… as you
