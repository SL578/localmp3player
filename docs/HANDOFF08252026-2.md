## What changed this session

Two commits, both pushed to `main` via a short-lived branch, fast-forwarded.

### `5605984` — Select everywhere, and an Untagged criterion

- **Playlists' Select moved to the leading side**, matching the Library, and
  gained Select All / Select None.
- **Tags gained multi-select twice over**: the tag list selects and batch-deletes
  tags; a tag's song list selects songs, with a bottom bar offering Add to
  Playlist, Like, and Remove from Tag.
- **Swiping Delete inside a tag was deleting the imported file.** `SongListContent`
  is shared by the library, tags and smart playlists and had one hardcoded
  destructive action. It now takes a `SongRemoval` — `.deleteFromLibrary` or
  `.detach(label:perform:)` — so the library still deletes and a tag detaches.
- **Smart playlists can require or exclude untagged songs.** `SmartRule` gained
  `includeUntagged` / `excludeUntagged`, stored as two more JSON keys.
- `SelectionAction` extracted so the bottom bars match.
- Select All compares set membership rather than counts, so a selection made
  before a search was narrowed no longer reads as "all selected".

### `68b32e9` — a real edit mode, and colors

- **Tag and playlist detail screens share one shape.** Edit (the sliders glyph)
  swaps the back button for Done and brings up Rename, Color, and a song
  selection; Shuffle, Add and Edit stand down. Nothing that only acts on a
  settled list stays up while editing, and nothing that only acts on the thing
  itself takes up room the rest of the time.
- **Editing a playlist selects as well as reorders** — ticks on the left, drag
  handles on the right.
- **Playlists and smart playlists carry a color.** New Core Data model version,
  `Colorable` protocol, one generic `EntityColorPicker`, and a `ColorSwatchGrid`
  split out for the smart playlist editor.
- **Tag and smart playlist titles are large now**, matching a playlist's.
- **Re-tapping the tab you are on returns that tab to its root.**
- Smart playlists lost Play All; `PlayAllButton` had no other caller and was
  deleted rather than left as dead code.

## Decisions worth not re-litigating

Carried over from the previous handoff, all still true:

**Never put a custom `ButtonStyle` in a List's environment.** `swipeActions`
builds its actions from the `Button`s you declare, and with a custom style in
scope it produces *none* — UIKit then disables the swipe entirely. Buttons inside
lists use `accentAction(theme)`.

**The palette goes on list content, not the app root.** An explicit
`foregroundStyle` outranks `.tint`, so setting it at the root repainted every
toolbar button in the text color.

**Tag exclusions use `SUBQUERY(...).@count == 0`, not `NOT (ANY tags.id == x)`.**
The SQL store turns that negation into "has some tag that isn't x", true of
anything carrying a second tag. Compiles fine, reads correctly, silently wrong.

**`SmartPlaylistDetailView` renders an array, not a `@FetchRequest`.** A rule can
end in a random sample, which no single fetch request expresses.

**Settings pushes by value.** A `NavigationLink` carrying its own destination
pushes through private state the `path` binding never sees.

**`EditButton` is not used anywhere.** It drives whatever `editMode` it finds
rather than the one the toolbar reads. Both detail screens hand-roll the toggle.

**Delete confirmations show only a Delete button.** iOS anchors them to the row
as a popover and drops the cancel button; tapping outside cancels.

**Sliders mean edit, a pencil means rename.** The user's own distinction.

New this session:

**The Core Data model got a new version rather than an edit in place.** Adding
`colorHex` to `Playlist` and `SmartPlaylist` by editing
`LocalLibrary.xcdatamodel` directly would have left an existing store with no
source model to infer a mapping from — the store metadata's version hashes would
match nothing in the bundle and the app would refuse to open it. `LocalLibrary
2.xcdatamodel` is the current version and both compile into the `.momd`. The
inferred-migration flags are now stated explicitly in `PersistenceController`
rather than relied on as defaults, so a change Core Data *can't* infer fails
loudly instead of appearing to work.

**Playlist selection is keyed by `PlaylistEntry.id`, not `Song.id`.** A playlist
may hold the same song twice; keying by song ticked both rows and removed the
wrong one. The songs behind a selection are de-duplicated before being liked or
added elsewhere.

**`onDelete` came off the playlist's `ForEach`.** In edit mode its red minus
circles land in exactly the place the selection ticks now occupy. Swiping a row
still offers Remove, so nothing was lost. `onMove` stays.

**Untagged joins the tag group rather than standing as its own clause**, so the
Any/All mode governs it. "All" plus Untagged is a contradiction — a song can't
carry every tag listed and no tags at all — and the editor says so in the section
footer instead of silently returning nothing. Excluding untagged is
`tags.@count > 0`.

**A smart playlist picks its color in its rule editor, not on its detail
screen.** That editor is what "edit this smart playlist" means, the way edit mode
is for a tag or a playlist — and it holds a draft that inserts nothing until
Save, so there is no object for `EntityColorPicker` to observe until then.
`ColorSwatchGrid` over a plain `Binding<String?>` is what both paths share.

**`EntityColorPicker` observes the object, not a binding to its color.** Writing
through a bare binding changes the store but publishes nothing, so the swatch
checkmark and the preview only catch up on reopen.

**Tapping the selected swatch clears the color.** Once "no color" means "draw in
the theme accent", it is a real state and needed a route back to it.

**Toolbar item budget on a pushed screen.** Four compact trailing icons fit
alongside a *short* inline title; five, or four with a long name, truncate it —
"Tag 1" survived, "New Smart Playlist" became "New Sm...". This is why Done moved
to the back button's place and why both detail screens now use large titles. If
you add a toolbar item, screenshot the result with a long name before believing
it fits.

**Tab panes are kept alive behind an opacity change, so they have no lifecycle
event to reset on.** `RootView` holds a per-tab counter (`popSignal`) that
`PlaylistsView` and `TagsView` take as `popToRoot` and watch with `onChange`.
Settings still resets its `NavigationPath` directly. This is the same constraint
that already forced `settingsPath` up into `RootView`.

## Known issues / open items

- **The rule migration path has still never met real data.** The code reads both
  older stored shapes, but neither simulator nor test data has exercised it. If
  any pre-rebuild smart playlists exist on the physical device, check them — a
  playlist reading as "every song" is the symptom.
- **The `colorHex` migration has only met the simulator's store.** It ran cleanly
  there with real data. The device's store is older and has not been tried. This
  is the first launch to watch after installing on hardware.
- **Tag colors and playlist colors fall back differently.** A playlist or smart
  playlist with `colorHex == nil` draws in the theme accent via `tint(theme)`; a
  tag with nil draws grey, because the tag call sites still use
  `Color(hex:) ?? .gray`. Tags previously always had a color assigned at
  creation, so nil was unreachable — clearing a swatch now makes it reachable.
  Worth unifying if it looks wrong in practice.
- **The Library tab is not wired to pop-to-root.** Its only push is Now Playing,
  and that state lives inside the shared `SongListContent` rather than in
  `LibraryView`, so the signal has to be threaded one level deeper. Offered and
  not done; the user knows.
- **The Library's toolbar collapses sort and import into a "..." menu while
  selecting.** Pre-existing, not a regression — Library already had Select All on
  the leading side. The same crowding was fixed on the tag screen by standing the
  non-edit actions down; Library has not had that treatment.
- **No test target.** Offered and explicitly declined in the previous session to
  avoid hand-editing `project.pbxproj`. Worth re-offering now that the project
  uses synchronized groups — a test target may no longer need that edit.
- **Drag-to-reorder is still unverified by automation.** The handles render, and
  now sit alongside selection ticks, but no drag has been performed.
- `ArtworkCache` still decodes synchronously on first hit.
- CarPlay entitlement still not requested. CarPlay code paths were untouched.
- **The user's `Test1` playlist changed order during testing** — verifying
  entry-based removal meant deleting the first `Blue Monday` and re-adding it,
  which appended it. Same five entries, different order. The user was told.

## Working notes for the simulator

The user **reversed** the earlier "don't use the simulator" instruction — driving
it is fine.

- **Horizontal swipes need a duration.** `swipe` with `duration: 0.8` works;
  instant swipes and `touch_path` land as *taps*, which at one point opened a
  playlist instead of revealing its row actions.
- Point space is 402 × 874 on iPhone 17. **Screenshots come back ~919 px wide
  regardless of the `scale` argument, so divide image coordinates by ~2.29.**
  Passing `scale: 0.4` did not change the returned size. `attach` reports the
  point dimensions — call it first.
- **A tab remembers where you left it**, so tapping a tab may land you on a
  pushed detail screen rather than the list you expected. Screenshot before
  tapping by coordinate; a tap meant for a list row otherwise lands on a song and
  starts playback. This bit twice this session.
- **The user tests alongside you in the same simulator.** Data changed under me
  mid-session in the previous session. Don't assume the app state is yours.
- **Put test data back.** Tags removed and re-added, colors set, playlists
  emptied — restore them and say what you couldn't restore exactly.
