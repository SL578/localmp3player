## Build and run

```bash
xcodebuild -project localmp3player.xcodeproj -scheme localmp3player -destination 'platform=iOS Simulator,name=iPhone 17' build
xcrun simctl install <UDID> <path>/localmp3player.app && xcrun simctl launch <UDID> com.lin.localmp3player
```

Builds clean, zero warnings. iOS 17.0 target. **There are two targets**, and the
app target embeds the extension, so building the app builds both.

To see only real diagnostics, anchor the grep to the start of the line —
`grep -iE "warning:|error:"` alone matches compiler *flags* in the echoed command
lines and buries you in 38KB of noise:

```bash
xcodebuild ... build 2>&1 | grep -E "^(/.*(warning|error):|\*\* BUILD)" | sort -u
```

### The stale-bundle trap, still true

`xcrun simctl install` exits 0 and creates a new bundle directory, but
`xcrun simctl launch <old-identifier>` starts whatever was installed under the
*old* identifier. **"BUILD SUCCEEDED" plus a successful install is not evidence
that the app on screen is your build.** After every install:

```bash
ps -Ao pid,comm | grep localmp3player          # which bundle is actually running
```

**Grepping the debug dylib for a new string only works if the change added
one.** This session's changes were a removed `role:`, a moved property and a
dropped modifier — no new literals, and a comment is not compiled in. What works
for any change is comparing the installed dylib against the build product:

```bash
shasum "$RUNNING_BUNDLE/localmp3player.debug.dylib" "$BUILD_PRODUCT/localmp3player.debug.dylib"
```

### `simctl uninstall` is never the answer

It **deletes the app's data container** — library, tags, playlists, palette,
interface mode, everything. `xcrun simctl install` over the existing install
registers new PlugIns fine.

If an uninstall is genuinely unavoidable, back the data container up *and verify
the copy* first:

```bash
cp -R "$(xcrun simctl get_app_container <UDID> com.lin.localmp3player data)/" backup/
```

### The scheme trap, if another target is ever hand-added

The project had **no `.xcscheme` files at all** — Xcode autocreated one per
target. Adding `ShareExtension` added a scheme, and with equal order hints Xcode
picks the alphabetically first: capital `S` sorts before lowercase `l`, so the
picker silently switched and ⌘R started asking "choose an app to run".

Fixed by committing a real shared scheme at
`localmp3player.xcodeproj/xcshareddata/xcschemes/localmp3player.xcscheme`, and
hiding the ShareExtension scheme in the user's `xcschememanagement.plist`
(`xcuserdata/` is gitignored, so that half is local only).

**Editing scheme files while Xcode is running does nothing.** The active scheme
lives in Xcode's in-memory UI state. Restarting Xcode is what applied it.

### Logging from the simulator

`NSLog` and `print` do **not** reach `xcrun simctl spawn <UDID> log show`, and
`--console-pty` redirected to a file captures nothing. What works is writing to a
file in the app's own Documents directory and reading it from the host.

## What changed this session

Four commits, all on `main`.

### 1. The delete row no longer animates out before the prompt (`59df086`)

**Symptom as reported:** *"Deleting a song will animate removing the song from
the list, then pop it back with the confirm delete message. It's jarring."*

**Cause:** the swipe action was `Button(role: .destructive)`. The role is what
tells UIKit the row is going away, and UIKit plays its row-removal animation the
moment the action fires — before the confirmation dialog exists. The action only
sets `pendingDelete` and destroys nothing, so the row slid out and then popped
back in behind the prompt.

The role is gone from the four actions that only raise a prompt — song, tag,
smart playlist, playlist. `.tint(.red)` was already stated explicitly from the
previous session, so the buttons are still red; the role was not carrying the
colour. **A full swipe still fires the action** — that does not depend on the
role, and it was checked both ways.

**The detach actions keep the role**: "Remove" from a playlist and
`SongRemoval.detach` really do remove their row on the spot, so there the
animation is telling the truth. The rule is written up on `confirmDelete` in
`DeleteConfirmation.swift`.

### 2. Artwork decodes off the main thread (`24b528d`)

`ArtworkCache.thumbnail` ran `UIImage(data:)` and `preparingThumbnail` inside
`ArtworkThumbnail`'s body. Every row scrolled into view for the first time paid
for a full-size JPEG decode on the main thread.

The decode is now `nonisolated` and reached through `Task.detached`. **The module
sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`** — an ordinary `async` method
in that file would still have run *on* the main actor and changed nothing. That
setting is in every one of the four build configurations; check it before
assuming anything in this codebase runs off-main.

Two details that are load-bearing:

- **The body still consults the cache synchronously.** That is a dictionary
  lookup and no decode, so a cached image draws immediately without writing any
  `@State`. Rows only write state on a first decode. This was deliberate: a row
  that invalidates itself while UIKit is configuring the cell can come up with no
  swipe actions, which is exactly how the like-swipe bug worked. **Swiping the
  first row on a cold launch was checked and works.**
- **The decoded image is tagged with the key it was decoded for.** Rows are
  recycled; an untagged one would show the previous song's cover.

### 3. The playback clock is its own object (`21bbcf0`)

`currentTime` was `@Published` on `PlaybackController`, so the 1 Hz ticker
republished the controller once a second and `RootView` — which observes it —
rebuilt all four tab panes' view structs every tick, the three off-screen ones
included.

It now lives on `PlaybackClock`, held by the controller as a **plain `let`**, so
a stored reference doesn't republish its owner. `ProgressSection` in
`NowPlayingView` observes the clock and wraps `ScrubBar` alone, so the tick's
invalidation stops there rather than rebuilding the whole player screen.

**There is deliberately no `currentTime` passthrough on the controller.** One
would compile at every call site and then silently never update. All six internal
uses say `clock.currentTime`.

Verified: elapsed time advances during playback, and seeking still moves it.

### 4. Three consistency fixes (`af3187d`)

**Tag colours fall back like playlist colours.** Playlists resolved a nil colour
through `Colorable.tint(_:)` to the theme accent; tags still used
`Color(hex:) ?? .gray`. Every *displayed* tag colour now uses `tint(theme)` —
`TagChip`, the Tags list, the tag detail toolbar swatch, `EntityColorPicker`'s
preview, the batch tag editor, and both smart-playlist criterion surfaces.
`resolved(tags:)` in `SmartPlaylistEditor` gained a `theme:` parameter for it.
`Binding.asColor` keeps grey and now says why: it is the swatch the system picker
opens on, and a `Binding` extension has no environment to read a theme from.

**Tag and smart-playlist detail screens show a title in Performance mode.**
`modeNavigationChrome` forced `.toolbarBackground(.visible)`, and on iOS 26 a bar
with a background hides a *large* navigation title outright. The colour is still
stated; only the forced visibility is gone. The bar is clear at the top of a
list, where the themed background shows through anyway, and takes the themed
colour once content scrolls under it — either way a flat fill, never a material.
Reproduced first (no title), then confirmed fixed ("Classical" visible).

**The Library tab goes back to its root.** It was the one tab whose reselect
signal nothing consumed, because it is also the one tab that never pushes — there
is no `navigationDestination` anywhere in `LibraryView`. Its root is the top of
an unfiltered list, so re-tapping it now clears the search text, closes the
search field, and scrolls the list to the top. `SongListContent` gained a
`scrollToTop: Int` signal and a `ScrollViewReader`; `SearchDismisser` is a
zero-sized view that has to sit **inside** the searchable scope, because
`\.dismissSearch` is only published to views the modifier encloses.

### Not the app: notification text-to-speech

Reported alongside the delete bug — *"suddenly text to speech for my
notifications turned on"* while listening through the app.

That is **Announce Notifications**, and no app can turn it on: there is no public
API, and the setting is changeable only by the user, by Siri, or by a Focus mode.
The project has no `AVSpeechSynthesizer`, no SiriKit entitlement and no intents;
the only audio code is `setCategory(.playback)` in `PlaybackController.swift`.

The app is why it was *noticed*, not why it was on: announcements only speak with
headphones or CarPlay connected, and the app declares the `audio` background mode
with a `.playback` session, so iOS treats it as a media app and ducks the music
to speak over it. Off switch: Settings → Notifications → Announce Notifications
(separate toggles for Headphones, CarPlay and Speaker). **Not re-confirmed by the
user yet** — if the toggle turns out to be off and it is still happening, that is
a genuinely odd one.

## Decisions worth not re-litigating

**A swipe action that only raises a confirmation must not carry
`role: .destructive`.** New this session. The role makes UIKit animate the row
away before the prompt appears. State `.tint(.red)` instead. Actions that really
do remove their row keep the role.

**`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` is set on this project.** New this
session. Anything that needs to be off the main thread must say so explicitly —
`nonisolated` plus `Task.detached`. A bare `async` function is not enough here,
even though it would be in a default-isolation module.

**`PlaybackClock` is held as a plain `let`.** New this session. Making it
`@Published`, or adding a `currentTime` passthrough on the controller, puts the
1 Hz rebuild straight back.

Carried over and still true:

**Don't hand-roll a gesture that competes with `List`'s own recognizers.** A song
row already carries the scroll view's pan, `swipeActions`' pan, and a tap. Adding
a fourth recognizer to shorten a swipe produced three defects and no benefit the
user valued. If a platform affordance's tuning is unsatisfying, the answer is to
live with it or change the interaction, not to reimplement the affordance.

**Never measure a List row with a `GeometryReader` that writes `@State`.** The
write lands during cell configuration and can leave `swipeActions` unbuilt. This
has now silently produced *no* swipe actions twice — see the `ButtonStyle` entry.
When a swipe stops revealing anything while scrolling still works, suspect row
body invalidation first.

**Never put a custom `ButtonStyle` in a List's environment.** `swipeActions`
builds its actions from the `Button`s you declare, and with a custom style in
scope it produces *none*. Buttons inside lists use `accentAction(theme)`.

**An explicit `foregroundStyle` outranks `.tint`** — which is why the palette
goes on list content rather than the app root, and why `role: .destructive`
needed `.tint(.red)` stated to beat the root tint.

**An SF Symbol does not inherit a foreground style set on its enclosing
`Button`; a `Text` does.** Colour toolbar glyphs on the `Image`, via
`ToolbarGlyph`; text buttons use `.toolbarTint()`.

**Test presentation dimming in Standard mode.** Performance mode has no
presentation animation to see it in.

**The mini bar is the only way into the full player.** Tapping a song plays it
and stays put. One player screen, one design, dismissed by a leading chevron.

**Multi-file sharing needs a share extension. Full stop.** The document-types
route delivers one URL, measured at the scene-delegate level. And **iOS will not
let a share extension launch its host app** — both `NSExtensionContext.open` and
the responder-chain fallback are refused, so the extension shows a card and the
user switches over themselves.

**Ordering matters in the extension.** Calling `completeRequest` before the
asynchronous `open` tears the extension down and the open never lands.

**One `PBXFileSystemSynchronizedRootGroup` can be listed in two targets'
`fileSystemSynchronizedGroups`**, which is how `Shared/` reaches both.

**Hand-adding a target adds a scheme.** Commit a shared `.xcscheme` for the app
at the same time.

**Tag exclusions use `SUBQUERY(...).@count == 0`,** not `NOT (ANY tags.id == x)`.

**`SmartPlaylistDetailView` renders an array, not a `@FetchRequest`.**

**Settings pushes by value.** **`EditButton` is not used anywhere.** **Delete
confirmations show only a Delete button.** **Sliders mean edit, a pencil means
rename.** **Core Data gets a new model version rather than an edit in place.**
**Playlist selection is keyed by `PlaylistEntry.id`.** **Toolbar item budget on a
pushed screen is four compact trailing icons with a short title.** **Tab panes
are kept alive behind an opacity change,** so `popSignal` exists.

**Don't trust `Slider.onEditingChanged` for "the drag ended" on iOS 26.** Any
control that needs to know when a finger lifted should own its own `DragGesture`.

**`ScrubBar` uses `highPriorityGesture`, not `gesture`.** It lives in a
`ScrollView` and a slightly diagonal scrub would otherwise be handed to the
scroll view mid-gesture. (This one is fine — it is not in a `List`.)

**A `play()` re-issue after setting `AVAudioPlayer.currentTime` is not needed.**
Tested with the line disabled: playback resumes on its own. Don't re-add it.

**`AudioFileStore.stageFile` must not delete its source unconditionally.**
`AudioFileStore.Origin` decides; only the picker's temp copies, the app's own
`Documents/Inbox`, and the share extension's shared inbox are disposable.

**An incoming share must not enter the scanning phase while the review sheet is
open.** `phase` leaving `.reviewing` makes `isPresentingReview` false, which the
sheet's dismissal binding reads as the user closing it.

**Incoming URLs are buffered for 400ms before staging.**

**Parser rules are deliberately narrow, each guarded by the case that would
break it.** `AC/DC`, `20 ft Under`, `Level 42`, `Sum 41` all survive.

## Known issues / open items

- **Move-or-delete-the-original on import is deliberately not built.** The user
  deferred it again this session — *"we might not be done with testing just
  yet"* — because copy-only is what allows repeat imports and deletions. To
  finish it: switch `DocumentPicker` to `asCopy: false`, hold the security scope
  from pick through commit, and delete on successful commit only. **Ask first
  whether it should move or delete, be a setting or the default, and confirm per
  file or run silently** — this is the one feature that destroys data if it is
  wrong.
- **The share extension cannot bring the app forward.** Not fixable from the app
  side. Worth re-testing on a physical device.
- **The Performance-mode toolbar background was only verified at rest.** New this
  session. With four songs in the simulator no screen using
  `modeNavigationChrome` has enough content to scroll under its bar, so the
  "content scrolled under the bar takes `theme.background`" half of the fix was
  reasoned about, not seen. The reasoning is that `toolbarBackground(_:for:)`
  sets *what* the background is and `.visible` only sets *whether* — so a
  material can't be substituted — but **it is worth one glance on the user's own
  larger library.**
- **`RootView` still rebuilds on every song change.** The 1 Hz rebuild is gone,
  but `RootView` observes `playback` only to re-inject it into the Now Playing
  sheet, and still rebuilds all four panes when `currentSong` or `isPlaying`
  publishes. That is user-initiated and rare, so it was left alone.
- **The `ArtworkCache` key still calls `data.hashValue` on every render.** Cheap
  in Foundation's sampling implementation, and unchanged from before, but it is
  the one main-thread cost left in that path.
- **The play/pause fade removal was never visually confirmed frame-by-frame.**
- **The rule migration path has still never met real data.**
- **The `colorHex` migration has only met the simulator's store.**
- **The Library's toolbar collapses sort and import into a "..." menu while
  selecting.** Pre-existing.
- **No test target.** Worth re-offering; the parser regressions are a ready-made
  first suite. This is the largest remaining item the user has not yet picked up.
- **Drag-to-reorder is still unverified by automation.**
- CarPlay entitlement still not requested; CarPlay paths untouched.
