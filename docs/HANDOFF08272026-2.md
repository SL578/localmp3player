## Build and run

```bash
xcodebuild -project localmp3player.xcodeproj -scheme localmp3player -destination 'platform=iOS Simulator,name=iPhone 17' build
xcrun simctl install <UDID> <path>/localmp3player.app && xcrun simctl launch <UDID> com.lin.localmp3player
```

Builds clean, zero warnings. iOS 17.0 target. **There are two targets**, and the
app target embeds the extension, so building the app builds both.

### The scheme trap, if another target is ever hand-added

The project had **no `.xcscheme` files at all** — Xcode autocreated one per
target. Adding `ShareExtension` added a scheme, and with equal order hints Xcode
picks the alphabetically first: capital `S` sorts before lowercase `l`, so the
picker silently switched and ⌘R started asking "choose an app to run".

Fixed by committing a real shared scheme at
`localmp3player.xcodeproj/xcshareddata/xcschemes/localmp3player.xcscheme`, and
hiding the ShareExtension scheme in the user's `xcschememanagement.plist`
(`xcuserdata/` is gitignored, so that half is local only).

**Editing scheme files while Xcode is running does nothing.** The active scheme
lives in Xcode's in-memory UI state. Restarting Xcode is what applied it.

### `simctl uninstall` is never the answer

It **deletes the app's data container** — library, tags, playlists, palette,
interface mode, everything. It was run in a previous session to make the
simulator notice a newly added share extension, and that was never necessary:
`xcrun simctl install` over the existing install registers new PlugIns fine.

If an uninstall is genuinely unavoidable, back the data container up *and verify
the copy* first:

```bash
cp -R "$(xcrun simctl get_app_container <UDID> com.lin.localmp3player data)/" backup/
```

### The stale-bundle trap, still true

`xcrun simctl install` exits 0 and creates a new bundle directory, but
`xcrun simctl launch <old-identifier>` starts whatever was installed under the
*old* identifier. **"BUILD SUCCEEDED" plus a successful install is not evidence
that the app on screen is your build.** After every install:

```bash
ps -Ao pid,comm | grep localmp3player          # which bundle is actually running
```

And to check the binary really has your change — the top-level `localmp3player`
executable is a thin stub, the code lives in the debug dylib:

```bash
LC_ALL=C grep -a -c "<a new string literal>" <app>/localmp3player.debug.dylib
```

This session used that both ways: `grep -c "heart.slash"` to prove the restored
code was in, and `grep -c "LikeSwipe"` returning **0** to prove the reverted code
was out.

### Logging from the simulator

`NSLog` and `print` do **not** reach `xcrun simctl spawn <UDID> log show`, and
`--console-pty` redirected to a file captures nothing. What works is writing to a
file in the app's own Documents directory and reading it from the host.

## What changed this session

### The swipe bug — `LikeSwipe` reverted and deleted

**Symptom as reported:** swiping around the app felt unresponsive. On a cold
launch the **first three rows** of a list would not swipe; row 4 would, and once
row 4 had been swiped, rows 1–3 started working. Changing the sort order made it
"work inconsistently" again. Tapping to play always worked. Swiping *right* to
like always worked. It happened on screens with no search bar too.

**Cause:** `LikeSwipe`, added in `697373c` the previous session, put a
`GeometryReader` in each song row's `.background` that wrote `@State` (`rowWidth`)
from `onAppear`. That invalidates the row **while UIKit is still configuring the
cell**, and `swipeActions` builds its actions from the `Button`s declared in the
row body at configuration time. The cells created in the List's very first layout
pass lost the race and came up with no swipe actions installed. Any later
relayout — scrolling, swiping another row, re-sorting — reconfigured them and
they started working.

That single cause explains every observation: only the first-pass cells; healed
by interacting elsewhere; inconsistent again after a re-sort; unaffected by the
search bar; and the SwiftUI gestures (tap, and `LikeSwipe`'s own drag) kept
working throughout because they don't depend on cell configuration.

Two further defects in the same 110 lines, found while reading it:

- **The axis lock was a directional deadzone.** The gesture committed to
  horizontal-or-vertical after 10pt, on whichever component was larger. A
  rightward swipe with any downward drift in its first 10pt locked to
  `.vertical` and then dropped every subsequent frame. The user reported feeling
  "a deadzone on each row" without being able to place it — this was it.
- **Gesture state never reset on cancellation.** `offset`, `axis` and `armed`
  were `@State`, cleared only in `onEnded`. SwiftUI never calls `onEnded` on a
  cancelled drag and offers no cancel callback at all — which is exactly what
  `@GestureState` exists for.

**The fix was to delete it,** at the user's call: *"I really don't think changing
the length of a swipe calls for inventing an entirely new library. Increases code
bloat anyways."* `LikeSwipe.swift` is gone and both call sites are back to
`swipeActions(edge: .leading)` with a Like/Unlike button — `SongList.swift`
(which backs Library, tag details and smart playlists) and `PlaylistsView.swift`
(`PlaylistDetailView`). Net −94 lines.

**The leading swipe is therefore back to UIKit's own full-swipe threshold**, which
measures at roughly two-thirds of the row width (a 270pt pull on a 402pt row
fires it). The user has accepted this: the shorter swipe was a preference, not a
requirement. **Do not rebuild it.** See the decision below.

### Delete is red

Every `Button(role: .destructive)` in a `swipeActions` block was rendering
**blue**, not red — the root `.tint(palette.accent)` in `ThemedRoot` outranks the
destructive role's own colour. Four swipe actions now state `.tint(.red)`:

- `SongList.swift` — Delete (library)
- `PlaylistsView.swift` — Delete a smart playlist, Delete a playlist
- `TagsView.swift` — Delete a tag

Plain `.red` rather than a palette entry: delete is a platform convention, not a
colour the user should be able to theme away.

**Deliberately left blue: the detach actions** — "Remove" from a playlist
(`PlaylistsView.swift`) and the `SongRemoval.detach` case (`SongList.swift`).
They carry `role: .destructive` for placement, but they only drop a reference and
destroy nothing, which is why they don't ask for confirmation either. Red against
blue now reads as "gone for good" against "just detached". Flagged to the user
with the veto offered; not yet ruled on.

The `role: .destructive` buttons in confirmation dialogs and alerts were already
red and were not touched.

## Decisions worth not re-litigating

**Don't hand-roll a gesture that competes with `List`'s own recognizers.** This
is the new one, and it cost a session. A song row already carries the scroll
view's pan, `swipeActions`' pan, and a tap. Adding a fourth recognizer to shorten
a swipe produced three defects and no benefit the user valued. If a platform
affordance's tuning is unsatisfying, the answer is to live with it or change the
interaction, not to reimplement the affordance.

**Never measure a List row with a `GeometryReader` that writes `@State`.** The
write lands during cell configuration and can leave `swipeActions` unbuilt. This
is the second time `swipeActions` has silently produced *nothing* in this app —
see the `ButtonStyle` entry below. When a swipe stops revealing anything while
scrolling still works, suspect row-body invalidation first.

Carried over and still true:

**Never put a custom `ButtonStyle` in a List's environment.** `swipeActions`
builds its actions from the `Button`s you declare, and with a custom style in
scope it produces *none*. Buttons inside lists use `accentAction(theme)`.

**An explicit `foregroundStyle` outranks `.tint`** — which is why the palette
goes on list content rather than the app root, and why `role: .destructive`
needed `.tint(.red)` stated to beat the root tint.

**An SF Symbol does not inherit a foreground style set on its enclosing
`Button`; a `Text` does.** Colour toolbar glyphs on the `Image`, via
`ToolbarGlyph`; text buttons use `.toolbarTint()`.

**Test presentation dimming in Standard mode.** Performance mode has no
presentation animation to see it in. UIKit sets `tintAdjustmentMode = .dimmed` on
the presenting view controller's view for as long as anything is presented over
it.

**The mini bar is the only way into the full player.** Tapping a song plays it
and stays put. One player screen, one design, dismissed by a leading chevron.

**Multi-file sharing needs a share extension. Full stop.** The document-types
route delivers one URL, measured at the scene-delegate level. And **iOS will not
let a share extension launch its host app** — both `NSExtensionContext.open` and
the responder-chain fallback are refused, so the extension shows a card and the
user switches over themselves.

**Ordering matters in the extension.** Calling `completeRequest` before the
asynchronous `open` tears the extension down and the open never lands.

**One `PBXFileSystemSynchronizedRootGroup` can be listed in two targets'
`fileSystemSynchronizedGroups`**, which is how `Shared/` reaches both. No build
file exception sets needed.

**Hand-adding a target adds a scheme.** Commit a shared `.xcscheme` for the app
at the same time.

**Tag exclusions use `SUBQUERY(...).@count == 0`,** not `NOT (ANY tags.id == x)`.

**`SmartPlaylistDetailView` renders an array, not a `@FetchRequest`.**

**Settings pushes by value.** **`EditButton` is not used anywhere.** **Delete
confirmations show only a Delete button.** **Sliders mean edit, a pencil means
rename.** **Core Data gets a new model version rather than an edit in place.**
**Playlist selection is keyed by `PlaylistEntry.id`.** **Toolbar item budget on a
pushed screen is four compact trailing icons with a short title.** **Tab panes
are kept alive behind an opacity change,** so `popSignal` exists.

**Don't trust `Slider.onEditingChanged` for "the drag ended" on iOS 26.** Any
control that needs to know when a finger lifted should own its own `DragGesture`.

**`ScrubBar` uses `highPriorityGesture`, not `gesture`.** It lives in a
`ScrollView` and a slightly diagonal scrub would otherwise be handed to the
scroll view mid-gesture. (This one is fine — it is not in a `List`.)

**A `play()` re-issue after setting `AVAudioPlayer.currentTime` is not needed.**
Tested with the line disabled: playback resumes on its own. Don't re-add it.

**`AudioFileStore.stageFile` must not delete its source unconditionally.**
`AudioFileStore.Origin` decides; only the picker's temp copies, the app's own
`Documents/Inbox`, and the share extension's shared inbox are disposable.

**An incoming share must not enter the scanning phase while the review sheet is
open.** `phase` leaving `.reviewing` makes `isPresentingReview` false, which the
sheet's dismissal binding reads as the user closing it.

**Incoming URLs are buffered for 400ms before staging.** How many callbacks a
share produces is not something the app gets to know.

**Parser rules are deliberately narrow, each guarded by the case that would
break it.** `AC/DC`, `20 ft Under`, `Level 42`, `Sum 41` all survive.

  `DocumentPicker` to `asCopy: false`, hold the security scope from pick through

  applies `modeNavigationChrome` with a large title, and a visible toolbar
  background hides a large navigation title on iOS 26. Pre-existing;
  `PlaylistDetailView` doesn't apply it and is fine.
- **`ArtworkCache` decodes synchronously on the main thread**, inside
  `ArtworkThumbnail`'s body, on every first hit per (image, size). Every row

  fixed — but a real source of scroll stutter, and the cheapest remaining
  performance win. Noted more precisely than in the previous handoff.
- **`RootView` re-evaluates its whole tree once a second.** It observes
  `playback` as an `@EnvironmentObject` and `PlaybackController.currentTime`
  publishes at 1 Hz, so every tick rebuilds all four tab panes' view structs —
  including the three that are off screen, with their own `List`s and search
  controllers. Nothing is visibly wrong, but the clock could be split into its
  own small observable that only `ScrubBar` and `MiniPlayerBar` depend on. New
  this session.
- **The play/pause fade removal was never visually confirmed frame-by-frame.**
- **`ワールドイズマイン CPK! Remix` keeps its remix name.** Judged that a remix
  name is part of the title; offered to strip trailing remix credits, awaiting a
  call.
- **The rule migration path has still never met real data.**
- **The `colorHex` migration has only met the simulator's store.**
- **Tag colors and playlist colors fall back differently** — playlists use
  `tint(theme)` for nil, tags still use `Color(hex:) ?? .gray`.
- **The Library tab is not wired to pop-to-root.**
- **The Library's toolbar collapses sort and import into a "..." menu while
  selecting.** Pre-existing.
- **No test target.** Worth re-offering; the parser regressions are a ready-made

## User preferences observed

complications in the future than good, tell me the potential consequences and

broken before theorising.

**Their symptom reports are precise and worth taking literally.** "The first
three rows", "after I swipe row 4 they start working", "there's a deadzone on
each row" each mapped onto a specific defect. The deadzone remark named a bug
